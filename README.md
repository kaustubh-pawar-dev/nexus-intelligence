# NEXUS Intelligence

**Enterprise Decision Intelligence & Predictive Analytics Platform** - a reproducible data engineering, business analytics, statistical analysis, churn modeling and dashboard project built entirely on synthetic enterprise data.

> **Data notice:** all data in this repository is synthetic and generated by the code in `src/nexus/datagen`. Figures, patterns and model results are simulated and say nothing about real companies or customers.

> **Status:** work in progress. Data engineering, data quality benchmarking, SQL analytics, statistical analysis, churn modeling and a four-page dashboard are implemented. Forecasting, anomaly detection, scenario analysis and intervention tracking are planned (see [Roadmap](#roadmap)).

## Business problem

Enterprise data arrives messy and spread across operational systems, and decisions built on it are only as good as the cleaning and analysis behind them. NEXUS simulates a company (suppliers, products, customers, orders, payments, refunds, purchase orders, inventory, shipments) and builds the analytics workflow on top of it: generate data, inject realistic defects, clean and validate it, analyse it with SQL and statistics, predict customer churn, and present the results in a dashboard. Every step is reproducible and tested.

## What is implemented

**Data engineering and data quality**
- Seeded synthetic data generation for 11 tables (about 236,000 rows) covering customers, orders, payments, refunds, purchasing, inventory, shipments and daily metrics.
- A defect benchmark: 17 defect types are injected into four tables and every change is recorded in a manifest, so the cleaning can be scored against a known answer.
- A layered PostgreSQL warehouse: `raw` (as delivered), `staging` (typed, deduplicated, with a row-level issue log), `analytics` (constraint-checked), plus `core` (the clean tables, used only to evaluate the pipeline) and `ml` (model scores).
- A cleaning pipeline that logs every row-level decision (fixed, flagged, dropped, quarantined) and proves that every raw row is accounted for.

**SQL analytics and statistics**
- 11 analytical SQL queries on a shared revenue definition: monthly revenue, category and segment contribution, product ranking, cohort retention, customer lifetime value, RFM segments, supplier performance, inventory turnover and revenue leakage.
- Data profiling and 7 hypothesis tests with effect sizes and Holm-corrected p-values, plus OLS and Poisson models with confounding checks (associations, not causal claims).

**Churn prediction**
- Churn is defined as no completed order in the 180 days after a monthly cutoff. Features use only information available before each cutoff (covered by tests), and the split is chronological with a gap equal to the outcome window.
- Baselines (random, recency rule, frequency rule), logistic regression and gradient boosting, compared with ROC-AUC, PR-AUC, precision, recall, F1, lift and Brier score, with customer-level bootstrap confidence intervals.
- Diagnostics: calibration by risk decile, flagging thresholds, stability across test cutoffs and odds ratios with intervals.
- Scoring of currently active customers into `ml.churn_scores`, with risk bands.

**Dashboard (Streamlit and Plotly)**
- Executive Overview: eight KPI cards with changes versus the previous period, revenue trend with 3-month average, year-over-year growth and category mix, with period filters.
- Customer Intelligence: cohort retention heatmap and curve, RFM segments and observed lifetime value.
- Predictive Risk: risk bands, spend by band and a filterable list of the highest-risk customers with CSV export.
- Data Quality: row accounting, cleaning actions, injected defects against pipeline actions, and the comparison with the ground truth.
- Every KPI query is reconciled by tests against independent queries and tables.

**Testing:**  automated tests (pytest). Last verified result on 2026-11-02:  passed.

## Technology stack

Python 3.10+, PostgreSQL, SQL, pandas, NumPy, SciPy, statsmodels, scikit-learn, SQLAlchemy, psycopg 3, Streamlit, Plotly, python-dotenv, pytest.

## Architecture

```
generators (seeded) -> data/raw (clean tables = ground truth)
                    -> data/raw/dirty (injected defects + defect manifest)
                              |
                     schema raw -> schema staging -> schema analytics
                                                          |
          SQL analytics, statistics, churn model -> schema ml (churn scores)
                                                          |
                          Streamlit dashboard (reads analytics and ml)

schema core holds the clean tables and is read only to evaluate the pipeline.
```

## Project structure

```
app/          Streamlit dashboard (streamlit_app.py and views/)
src/nexus/    library code: data generation, cleaning, promotion, SQL analytics,
              statistics, churn modeling, dashboard data layers and view models
scripts/      runnable entry points (generate, load, build, analyse, score, check)
sql/          schema.sql, analytics/ and dashboard/ queries
tests/        pytest suite
docs/         data_dictionary.md and images/ (screenshots)
```

## Setup (Windows, PowerShell)

Requires Python 3.10+ and a local PostgreSQL server.

```powershell
git clone https://github.com/kaustubh-pawar-dev/nexus-intelligence.git
cd nexus-intelligence
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements-dev.txt
pip install -e .
Copy-Item .env.example .env
```

Edit `.env` and set `NEXUS_DB_PASSWORD` (never commit `.env`).

Create the database and role once (example; adjust to your PostgreSQL setup and use your own password):

```powershell
psql -U postgres -c "CREATE ROLE nexus_app LOGIN PASSWORD 'your-password-here';"
psql -U postgres -c "CREATE DATABASE nexus_intelligence OWNER nexus_app;"
```

```powershell
python scripts/check_environment.py

python scripts/generate_order_data.py

python scripts/generate_purchase_order_data.py
python scripts/generate_inventory_data.py
python scripts/generate_shipment_data.py
python scripts/generate_daily_metrics_data.py
python scripts/generate_dirty_data.py

# 2. Build the database layers
python scripts/init_database.py
python scripts/load_core.py
python scripts/load_raw.py
python scripts/build_staging.py
python scripts/build_analytics.py

# 3. Analyse
python scripts/run_sql_analytics.py
python scripts/run_sql_analytics_2.py

# 4. Churn model and scoring
python scripts/run_churn.py
```

`scripts/summarize_*.py` and `scripts/check_dashboard_data.py` print checks for each stage. See `docs/data_dictionary.md` for table definitions, defect types and metric definitions.

## Running the dashboard

```powershell
python -m streamlit run app/streamlit_app.py
```

The dashboard opens at http://localhost:8501. It reads the `analytics` and `ml` schemas (and `core` plus the defect manifest on the Data Quality page), so run the pipeline above first.

## Limitations

- All data is simulated, so model quality and business figures demonstrate the method only. The dataset defines no currency.
- Churn means no completed order in 180 days. This counts infrequent buyers who are simply between orders as churned.
- The train and test sets split by time, so the same customers can appear in both at different dates.
- Churn scores rank customers better than chance but are not exact probabilities (see the calibration results).
- Statistical results are associations, not causal effects. Correlated features share effects.
- The dashboard reads the cleaned layer, which holds out the 0.92% of revenue that sits in quarantined orders.
