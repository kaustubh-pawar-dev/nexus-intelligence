# Data Dictionary

> **All data in this project is SYNTHETIC**, generated by code in this repository.
> It does not describe any real company, customer or supplier.

Observation window: 2023-01-01 to 2025-12-31 (fixed, so results are reproducible).
Default random seed: 42. Each table uses its own random stream derived from `[seed, stream_id]`.

## suppliers (24 rows)

| Column | Type | Description |
|---|---|---|
| supplier_id | string, PK | Format `SUP-0001`. |
| supplier_name | string | Fictional name, unique. |
| country | string | Supplier country, one of 10 configured countries. |
| region | string | Region derived from country. |
| lead_time_mean_days | integer | Average order-to-delivery days. Based on a country baseline plus noise, minimum 3. |
| on_time_delivery_rate | decimal | Underlying probability a delivery arrives on time, between 0.70 and 0.995. Drives simulated delays in later steps. |
| defect_rate | decimal | Underlying share of defective units, between 0 and 0.08. |
| payment_terms_days | integer | One of 15, 30, 45, 60, 90. |
| onboarded_date | date | When the supplier was onboarded. Always before 2023-01-01. |

## products (120 rows)

| Column | Type | Description |
|---|---|---|
| product_id | string, PK | Format `PRD-0001`. |
| sku | string, unique | Format `SKU-<CATEGORY CODE>-0001`. |
| product_name | string | Fictional product name. |
| category | string | One of 6 categories, 20 products each. |
| supplier_id | string, FK | References `suppliers.supplier_id`. |
| unit_cost | decimal | Cost per unit, at least 2.00. Sampled log-uniformly within a category range. |
| list_price | decimal | `unit_cost * (1 + markup)`, with a category-specific markup. Always greater than `unit_cost`. |
| launch_date | date | Between 2020-01 and mid-2024. |
| is_active | boolean | Status flag as of 2025-12-31. About 8% of products are inactive. |

## Known simplifications

- These two tables are clean. Deliberate data-quality defects are injected in a later step.
- Categories are evenly balanced (20 each) for simplicity, which real catalogs rarely are.
## customers (5,000 rows)

| Column | Type | Description |
|---|---|---|
| customer_id | string, PK | Format `CUST-00001`. Assigned in signup order. |
| email | string, unique | Fictional address at the reserved domain `example.com`. |
| country | string | One of 8 countries, sampled with fixed weights (India 28%, United States 24%, ...). |
| region | string | Region derived from country. |
| segment | string | `Consumer` (70%), `Small Business` (22%) or `Enterprise` (8%). |
| acquisition_channel | string | One of 6 channels: Organic Search, Paid Search, Social Media, Email, Referral, Direct. |
| signup_date | date | Between 2021-01-01 and 2025-12-31. Daily signup weight rises linearly, so the customer base grows. About 28% of customers signed up before the 2023-01-01 analysis window. |
| marketing_opt_in | boolean | True for about 62% of customers. |

Notes:
- Purchase behavior, churn and refunds are **not** stored here. They are generated in the transactions step.
- The customers table is clean. Duplicates and missing values are injected in a later data-quality step.
- Customer attributes are simplified: no names, addresses or ages, and every email is a fictional `example.com` address.

## orders (row count depends on the seed; see the summary script)

| Column | Type | Description |
|---|---|---|
| order_id | string, PK | Format `ORD-000001`. Assigned in order-date order. |
| customer_id | string, FK | References `customers.customer_id`. Orders are never earlier than the customer's signup date. |
| order_date | date | Between 2023-01-01 and 2025-12-31. Weighted by month seasonality (peak in November and December) and a weekday factor. |
| sales_channel | string | `Web` (55%), `Mobile App` (35%) or `Marketplace` (10%). |
| order_status | string | `Completed` or `Cancelled` (about 4%). |
| discount_pct | decimal | Order-level discount: 0, 0.05, 0.10, 0.15 or 0.20. About 20% of orders are discounted, and about 45% in November. |

## order_items (row count depends on the seed; see the summary script)

| Column | Type | Description |
|---|---|---|
| order_id | string, FK | References `orders.order_id`. Together with `line_number` it forms the primary key. |
| line_number | integer | Position of the line within the order, starting at 1. |
| product_id | string, FK | References `products.product_id`. A product appears at most once per order. |
| quantity | integer | Between 1 and 20. Larger on average for Small Business and Enterprise customers. |
| unit_price | decimal | The product's `list_price` (constant over time in this simulation). |
| unit_cost | decimal | Cost of goods sold per unit, a snapshot of the product's `unit_cost`. |
| discount_pct | decimal | Copy of the order's `discount_pct`. |
| line_total | decimal | `round(quantity * unit_price * (1 - discount_pct), 2)`. Revenue before any refund. |

Notes and simplifications:
- Order behavior is built into the simulation: Enterprise customers order more often than Consumers. Paid Search and Social Media customers have shorter lifespans, and Referral customers have longer ones. Customers who opted in to marketing order slightly more. These are simulation settings, not real-world findings.
- Each customer stops ordering after a random lifetime from signup (churn). The lifetime is not stored, so churn must be inferred from order behavior.
- Orders exist only inside the 2023-2025 window. Customers who signed up in 2021 or 2022 have no generated history before 2023.
- Products cannot sell before `launch_date`. Inactive products are not sold in the last 180 days of the window.
- Cancelled orders keep their lines. Revenue metrics must exclude them.
- Payments, refunds and shipping are generated in later steps. Prices do not change over time. There is no tax or shipping charge.
