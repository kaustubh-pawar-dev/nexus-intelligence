# Data Dictionary

> **All data in this project is SYNTHETIC**, generated by code in this repository.
> It does not describe any real company, customer or supplier.

Observation window: 2023-01-01 to 2025-12-31 (fixed, so results are reproducible).
Default random seed: 42. Each table uses its own random stream derived from `[seed, stream_id]`.

## suppliers (24 rows)

| Column | Type | Description |
|---|---|---|
| supplier_id | string, PK | Format `SUP-0001`. |
| supplier_name | string | Fictional name, unique. |
| country | string | Supplier country, one of 10 configured countries. |
| region | string | Region derived from country. |
| lead_time_mean_days | integer | Average order-to-delivery days. Based on a country baseline plus noise, minimum 3. |
| on_time_delivery_rate | decimal | Underlying probability a delivery arrives on time, between 0.70 and 0.995. Drives simulated delays in later steps. |
| defect_rate | decimal | Underlying share of defective units, between 0 and 0.08. |
| payment_terms_days | integer | One of 15, 30, 45, 60, 90. |
| onboarded_date | date | When the supplier was onboarded. Always before 2023-01-01. |

## products (120 rows)

| Column | Type | Description |
|---|---|---|
| product_id | string, PK | Format `PRD-0001`. |
| sku | string, unique | Format `SKU-<CATEGORY CODE>-0001`. |
| product_name | string | Fictional product name. |
| category | string | One of 6 categories, 20 products each. |
| supplier_id | string, FK | References `suppliers.supplier_id`. |
| unit_cost | decimal | Cost per unit, at least 2.00. Sampled log-uniformly within a category range. |
| list_price | decimal | `unit_cost * (1 + markup)`, with a category-specific markup. Always greater than `unit_cost`. |
| launch_date | date | Between 2020-01 and mid-2024. |
| is_active | boolean | Status flag as of 2025-12-31. About 8% of products are inactive. |

## Known simplifications

- These two tables are clean. Deliberate data-quality defects are injected in a later step.
- Categories are evenly balanced (20 each) for simplicity, which real catalogs rarely are.
## customers (5,000 rows)

| Column | Type | Description |
|---|---|---|
| customer_id | string, PK | Format `CUST-00001`. Assigned in signup order. |
| email | string, unique | Fictional address at the reserved domain `example.com`. |
| country | string | One of 8 countries, sampled with fixed weights (India 28%, United States 24%, ...). |
| region | string | Region derived from country. |
| segment | string | `Consumer` (70%), `Small Business` (22%) or `Enterprise` (8%). |
| acquisition_channel | string | One of 6 channels: Organic Search, Paid Search, Social Media, Email, Referral, Direct. |
| signup_date | date | Between 2021-01-01 and 2025-12-31. Daily signup weight rises linearly, so the customer base grows. About 28% of customers signed up before the 2023-01-01 analysis window. |
| marketing_opt_in | boolean | True for about 62% of customers. |

Notes:
- Purchase behavior, churn and refunds are **not** stored here. They are generated in the transactions step.
- The customers table is clean. Duplicates and missing values are injected in a later data-quality step.
- Customer attributes are simplified: no names, addresses or ages, and every email is a fictional `example.com` address.

## orders (row count depends on the seed; see the summary script)

| Column | Type | Description |
|---|---|---|
| order_id | string, PK | Format `ORD-000001`. Assigned in order-date order. |
| customer_id | string, FK | References `customers.customer_id`. Orders are never earlier than the customer's signup date. |
| order_date | date | Between 2023-01-01 and 2025-12-31. Weighted by month seasonality (peak in November and December) and a weekday factor. |
| sales_channel | string | `Web` (55%), `Mobile App` (35%) or `Marketplace` (10%). |
| order_status | string | `Completed` or `Cancelled` (about 4%). |
| discount_pct | decimal | Order-level discount: 0, 0.05, 0.10, 0.15 or 0.20. About 20% of orders are discounted, and about 45% in November. |

## order_items (row count depends on the seed; see the summary script)

| Column | Type | Description |
|---|---|---|
| order_id | string, FK | References `orders.order_id`. Together with `line_number` it forms the primary key. |
| line_number | integer | Position of the line within the order, starting at 1. |
| product_id | string, FK | References `products.product_id`. A product appears at most once per order. |
| quantity | integer | Between 1 and 20. Larger on average for Small Business and Enterprise customers. |
| unit_price | decimal | The product's `list_price` (constant over time in this simulation). |
| unit_cost | decimal | Cost of goods sold per unit, a snapshot of the product's `unit_cost`. |
| discount_pct | decimal | Copy of the order's `discount_pct`. |
| line_total | decimal | `round(quantity * unit_price * (1 - discount_pct), 2)`. Revenue before any refund. |

Notes and simplifications:
- Order behavior is built into the simulation: Enterprise customers order more often than Consumers. Paid Search and Social Media customers have shorter lifespans, and Referral customers have longer ones. Customers who opted in to marketing order slightly more. These are simulation settings, not real-world findings.
- Each customer stops ordering after a random lifetime from signup (churn). The lifetime is not stored, so churn must be inferred from order behavior.
- Orders exist only inside the 2023-2025 window. Customers who signed up in 2021 or 2022 have no generated history before 2023.
- Products cannot sell before `launch_date`. Inactive products are not sold in the last 180 days of the window.
- Cancelled orders keep their lines. Revenue metrics must exclude them.
- Payments, refunds and shipping are generated in later steps. Prices do not change over time. There is no tax or shipping charge.


## payments (one row per completed order; see the summary script for counts)

| Column | Type | Description |
|---|---|---|
| payment_id | string, PK | Format `PAY-000001`. |
| order_id | string, FK, unique | References `orders.order_id`. Only `Completed` orders have a payment. |
| payment_date | date | Order date plus 0 to 3 days (bank transfers take 1 to 7 extra days). Clipped at 2025-12-31. |
| payment_method | string | Credit Card, Debit Card, UPI, Net Banking, Digital Wallet or Bank Transfer. The mix depends on the customer segment (Enterprise mostly pays by bank transfer). |
| payment_status | string | `Captured` or `Failed`. The failure probability depends on the method (Net Banking is the highest at 6%). A `Failed` payment on a completed order is simulated uncollected revenue. |
| amount | decimal | Sum of the order's `line_total` values. |

## refunds (see the summary script for counts)

| Column | Type | Description |
|---|---|---|
| refund_id | string, PK | Format `REF-000001`, assigned in refund-date order. |
| payment_id | string, FK, unique | References `payments.payment_id`. Only `Captured` payments can be refunded, at most once each. |
| order_id | string, FK | References `orders.order_id`, consistent with the payment. |
| refund_date | date | Payment date plus 3 to 30 days. Refunds that would fall after 2025-12-31 are not generated. |
| refund_type | string | `Full` (about 60%, equals the payment amount) or `Partial` (20% to 80% of the payment amount). |
| refund_reason | string | Defective, Not As Described, Changed Mind, Late Delivery or Wrong Item. The `Defective` share rises with the order's supplier defect score. |
| refund_amount | decimal | Amount returned to the customer. Never above the payment amount. |

Notes and simplifications:
- Refund probability per captured payment is `0.02 + 2.0 * defect score`, where the defect score is the line-value-weighted `defect_rate` of the suppliers behind the order's products. This link is a simulation setting, not a real-world finding.
- Refunds are right-censored: late-2025 payments have less time to be refunded, so refund rates in the final weeks understate the true rate.
- There are no payment retries, installments, chargebacks or partial captures. Cancelled orders have no payment and no refund.
- Net revenue calculations later in the project must use captured payment amounts minus refunds, and must label failed payments as uncollected.

## purchase_orders (at most one replenishment order per product per month; see the summary script for counts)

| Column | Type | Description |
|---|---|---|
| po_id | string, PK | Format `PO-000001`, assigned in order-date order. |
| supplier_id | string, FK | References `suppliers.supplier_id`. Always the supplier of the product. |
| product_id | string, FK | References `products.product_id`. |
| order_date | date | A random day within the month, between 2023-01-01 and 2025-12-31. |
| expected_delivery_date | date | `order_date` plus the supplier's `lead_time_mean_days` (the planned lead time). |
| actual_delivery_date | date, nullable | Expected date plus a delay. Empty when `delivery_status` is `In Transit`. |
| delivery_status | string | `Delivered` or `In Transit` (the delivery would land after 2025-12-31). |
| quantity_ordered | integer | Order-up-to policy: `max(5, ceil(demand over lead time + 45 days * 1.15 * noise - inventory position))`. See the notes. |
| quantity_received | integer, nullable | Equals the ordered quantity, or 5% to 30% fewer for about 5% of deliveries. Empty when in transit. |
| defective_units | integer, nullable | Binomial draw of received units with the supplier's `defect_rate`. Empty when in transit. |
| unit_cost | decimal | Snapshot of the product's `unit_cost`. |
| order_cost | decimal | `round(quantity_ordered * unit_cost, 2)`. |

Notes and simplifications:
- Each delivery is on time with probability equal to the supplier's `on_time_delivery_rate`, reduced by 0.06 for orders placed in October to December. On-time deliveries arrive 0 to 2 days early, and late ones arrive 1 plus a Poisson(4) number of days late. These are simulation settings, not real-world findings.
- The three nullable columns are the only intentional nulls. They are empty only for `In Transit` rows, which are right-censored by the end of the observation window.
- Order quantities follow a stock-aware order-up-to policy. At the order date the buyer targets the actual unit sales over the planned lead time plus 45 days, multiplied by a 1.15 safety buffer and forecast noise (sigma 0.10), and orders the difference to the current inventory position (stock received or scheduled, net of defective units that are written off on arrival, minus past sales; the buyer is assumed to know a delivery's defect count). A month where the position already covers the target gets no order. Using actual future sales is a stand-in for a forecast. Each product also starts with initial stock (45 days of demand times 1.25 on its first listed day) that is not a purchase order.
- Inactive products are not replenished in the last 180 days of the window.
- Planned lead times are constant per supplier, and there is no minimum order quantity, freight cost or order consolidation.


## inventory_daily (one row per product per listed day; see the summary script for counts)

| Column | Type | Description |
|---|---|---|
| product_id | string, FK | References `products.product_id`. Together with `date` it forms the primary key. |
| date | date | From the product's first listed day (its `launch_date`, or 2023-01-01 for older products) to 2025-12-31, with no gaps. |
| opening_stock | integer | Units on hand at the start of the day. Equals the previous day's `closing_stock`, and 0 on the first day. |
| initial_stock_units | integer | Opening stock placed on the first listed day (45 days of demand times 1.25, minimum 5). 0 on every other day. It is not a purchase order. |
| po_receipts_units | integer | Units received from purchase orders that arrived that day (`quantity_received`). Arrivals before the first listed day are counted on that day. |
| defective_writeoff_units | integer | Defective units among the day's receipts, written off from stock on arrival. |
| units_demanded | integer | Units on completed orders placed that day. |
| units_fulfilled | integer | Units shipped that day, including units that cleared earlier backorders. |
| closing_stock | integer | Units on hand at the end of the day. Never negative. |
| backorder_units | integer | Cumulative unmet demand at the end of the day. Never both positive with `closing_stock`. |
| stockout_flag | integer | 1 when `backorder_units` is above 0, otherwise 0. |
| inventory_value | decimal | `round(closing_stock * unit_cost, 2)`, at cost. |

Identities:
- `closing_stock = opening_stock + initial_stock_units + po_receipts_units - defective_writeoff_units - units_fulfilled`
- `backorder_units = previous backorder_units + units_demanded - units_fulfilled`

Notes and simplifications:
- Unmet demand is carried forward as backorders. Customers wait and do not cancel, so a stockout creates delay but no lost sales in this table. Lost-sales assumptions belong to the scenario step.
- Stock is derived from the generated purchase orders and sales, and is not simulated separately. There are no stock counts, shrinkage, returns to stock or transfers. Refunded units are not returned to stock.
- Orders that are `In Transit` at the end of the window are not counted as receipts.
- The table is tied to the stock-aware purchase orders from Step 8. A change to the purchasing settings changes this table.

## shipments (one row per completed order; see the summary script for counts)

| Column | Type | Description |
|---|---|---|
| shipment_id | string, PK | Format `SHP-000001`, assigned in order-id order. |
| order_id | string, FK, unique | References `orders.order_id`. Only `Completed` orders have a shipment. |
| carrier | string | SwiftShip, BlueLine Express, GlobalPost or RapidRoute. Chosen independently of region. |
| ship_date | date, nullable | Order date plus `handling_days`. Empty when `shipment_status` is `Awaiting Shipment`. |
| promised_delivery_date | date | Order date plus 2 processing days, the regional base transit days and 1 buffer day. Depends only on the customer's region. |
| delivered_date | date, nullable | `ship_date` plus `transit_days`. Empty unless the status is `Delivered`. |
| shipment_status | string | `Delivered`, `In Transit` (shipped but not delivered by 2025-12-31) or `Awaiting Shipment` (dispatch would fall after 2025-12-31). |
| had_backorder | integer | 1 when any product on the order had backorders (`stockout_flag` = 1 in `inventory_daily`) on the order date. |
| handling_days | integer, nullable | Days from order to dispatch: 0 to 2 normally, plus 2 and a Poisson(4) number of days when `had_backorder` is 1. |
| transit_days | integer, nullable | Days from dispatch to delivery. Depends on region and carrier speed, with a random jitter and occasional disruptions. |
| delivery_delay_days | integer, nullable | `delivered_date - promised_delivery_date`. Positive means late. |
| shipping_cost | decimal | Cost to the business: regional base cost times a carrier multiplier, plus 8% per extra order line. Not charged to customers. |

Notes and simplifications:
- Slower carriers have a higher late-delivery probability, and orders in backorder are dispatched later. These are simulation settings, not real-world findings.
- The three blank-field groups are the only intentional nulls. They exist because of right-censoring at the end of the observation window.
- A refund reason of `Late Delivery` in `refunds` is not linked to actual shipment lateness, so refund behavior is independent of delivery delay in this simulation.
- There is no weight, volume, tracking, damage or return shipping.

## daily_metrics (one row per calendar day, 2023-01-01 to 2025-12-31; 1,096 rows)

A deterministic aggregation of the other tables. It has no random draws, and every column total reconciles to its source table.

| Column | Type | Basis | Description |
|---|---|---|---|
| date | date, PK | | Calendar day. No gaps. |
| orders_placed | integer | order date | All orders placed that day, including cancelled ones. |
| orders_completed | integer | order date | Orders with status `Completed`. |
| orders_cancelled | integer | order date | Orders with status `Cancelled`. `orders_placed = orders_completed + orders_cancelled`. |
| new_customers | integer | signup date | Customers whose `signup_date` is that day. Signups before 2023-01-01 are not counted here. |
| active_customers | integer | order date | Distinct customers with at least one completed order that day. |
| units_sold | integer | order date | Units on completed orders. |
| gross_revenue | decimal | order date | Sum of `line_total` of completed orders, after order discounts and before refunds. Failed payments are not deducted. |
| discount_amount | decimal | order date | `sum(quantity * unit_price)` minus `gross_revenue`. |
| cogs | decimal | order date | Cost of goods sold: `sum(quantity * unit_cost)` of completed orders. |
| gross_margin | decimal | order date | `gross_revenue - cogs`. Before shipping, refunds and failed payments, so it is not a full profit measure. |
| shipping_cost | decimal | order date | Shipping cost of the shipments of that day's completed orders. A cost to the business. |
| payments_captured | decimal | payment date | Amount of captured payments that landed that day. |
| payments_failed | decimal | payment date | Amount of failed payments that day. Simulated uncollected revenue. |
| refunds_amount | decimal | refund date | Amount refunded that day. |
| po_spend | decimal | PO order date | `order_cost` of purchase orders placed that day. Procurement spend, not cost of goods sold. |
| listed_products | integer | date | Products listed that day (rows of `inventory_daily`). |
| products_in_stockout | integer | date | Listed products with backorders at the end of the day. |
| backorder_units | integer | date | Total backorder units at the end of the day. |
| inventory_value | decimal | date | Total closing stock at cost. |

Notes and simplifications:
- Two bases are kept separate on purpose. Order-basis columns use the order date. Cash-basis columns use the payment or refund date, so on a single day they differ from revenue, while their totals over the window match.
- Net cash collected is `payments_captured - refunds_amount`. Failed payments are never netted into revenue, and are reported as uncollected.
- Orders from late 2025 have had less time to be paid or refunded, so cash and refund columns at the end of the window understate the true figures (right-censoring).
- The table contains no lost-sales estimate for stockouts. Those assumptions belong to the scenario step.

## Injected data-quality defects (the "as delivered" layer in data/raw/dirty)

The clean CSVs in `data/raw/` are the **ground truth**. `data/raw/dirty/` is an "as delivered" copy used by the database and data-engineering steps. Four tables carry injected defects, and the other seven are copied unchanged. `defect_manifest.csv` records every injected change so the cleaning pipeline can be scored. The pipeline itself must never read the manifest.

| Table | Defect type | Rate | What is injected |
|---|---|---|---|
| customers | exact_duplicate_row | 1.2% | A copy of an untouched row appended at the end of the file. |
| customers | missing_email | 2% | `email` left empty. |
| customers | country_variant | 1.5% | `country` written as `USA`, `UK`, `UAE` or in lower case. `region` is left unchanged. |
| customers | future_signup_date | 0.3% | `signup_date` 30 to 399 days after 2025-12-31. |
| orders | exact_duplicate_row | 0.8% | Appended copy of an untouched row. |
| orders | date_format_dmy | 1% | `order_date` written as `dd/mm/yyyy` instead of `yyyy-mm-dd`. Days up to 12 are ambiguous with months. |
| orders | missing_customer_id | 0.4% | `customer_id` left empty. |
| orders | unknown_customer_id | 0.4% | `customer_id` set to `CUST-99999`, which does not exist. |
| orders | invalid_discount_pct | 0.6% | `discount_pct` set to 1.5 (valid values are 0 to 0.20). |
| orders | status_case_variant | 1.5% | `order_status` in lower case. |
| order_items | exact_duplicate_row | 0.5% | Appended copy of an untouched row. |
| order_items | negative_quantity | 0.2% | `quantity` multiplied by -1. |
| order_items | missing_line_total | 0.3% | `line_total` left empty. |
| order_items | zero_unit_price | 0.2% | `unit_price` set to 0. |
| payments | exact_duplicate_row | 0.4% | Appended copy of an untouched row. |
| payments | missing_amount | 0.3% | `amount` left empty. |
| payments | method_case_variant | 2% | `payment_method` in lower case. |

Rates apply to each table's clean row count, rounded to a whole number of rows.

### defect_manifest.csv

| Column | Description |
|---|---|
| table | The affected table. |
| row_key | Primary key of the affected row (`order_id\|line_number` for `order_items`). |
| defect_type | One of the types above. |
| column | The changed column. Empty for `exact_duplicate_row`. |
| original_value | Value in the clean table, as text. Empty when the original was empty. |
| injected_value | Value in the dirty table, as text. Empty when the injected value is empty. |

Notes and simplifications:
- Each row has at most one cell defect, and duplicates are copies of rows with no cell defect, so the manifest is exact and defect groups never overlap.
- Other tables are not made dirty. An order whose `customer_id` was damaged still has a valid payment and shipment. Cleaning must recover that link.
- `daily_metrics.csv` is derived from the clean data. Totals computed from the cleaned dirty layer should reconcile to it.
- The defect types and rates are simulation settings, not real-world error rates.

## PostgreSQL model (schema `core`)

`sql/schema.sql` creates the cleaned relational model in the `core` schema of the `nexus_intelligence` database. It has the same 11 tables as the CSV files, with the same column names. The schema holds no data until the loading step.

| Aspect | Design |
|---|---|
| Keys | Every table has a primary key. 11 foreign keys connect the tables: products to suppliers, orders to customers, order_items to orders and products, payments to orders, refunds to payments and orders, purchase_orders to suppliers and products, inventory_daily to products, and shipments to orders. |
| Types | Money columns are `numeric`, never floating point. Dates are `date`. Flags such as `stockout_flag` are `smallint` with a 0 or 1 check. Categorical columns use `CHECK ... IN` lists. |
| Rules enforced | `list_price > unit_cost`. Order, signup and inventory dates fall inside the observation window. Purchase orders and shipments must have exactly the delivery fields their status allows. The inventory stock identity and the stockout flag are checked. `orders_placed = orders_completed + orders_cancelled`. |
| Nullable | `customers.email` (the missing-value policy decides whether a gap is recovered or rejected), and the delivery fields of in-transit purchase orders and open shipments. |
| Not enforced | `line_total = round(quantity * unit_price * (1 - discount), 2)`. It is reconciled in the data-engineering step instead. |
| Indexes | 14 indexes on foreign keys, date filters and a partial index for stockout days. |
| Layers | `core` is the cleaned model. The "as delivered" files from `data/raw/dirty` are loaded into a separate `raw` schema, as text, in the data-engineering step. |

Notes and simplifications:
- The window dates (2021 to 2025) are hard-coded in check constraints, as simulation settings.
- `sql/schema.sql` is idempotent. `python scripts/init_database.py --reset` drops and recreates `core` and destroys any loaded data.
- The database password lives only in the git-ignored `.env`.

## Loading the clean data into PostgreSQL

`python scripts/load_core.py` loads the 11 clean CSV files from `data/raw` into `core` using PostgreSQL `COPY`, in foreign-key order, inside one transaction. The tables are truncated first, so the load can be repeated. Any error rolls the whole load back.

After loading, the script reconciles the database against the files:

| Check | What it compares |
|---|---|
| Row counts | Each table against its CSV row count. |
| Orphans | Nine joins that must return zero rows, such as completed orders without a payment or a shipment. |
| Business totals | Revenue, cost of goods sold, captured and failed payments, refunds, shipping cost, purchase spend and inventory value, computed by SQL, against the totals of `daily_metrics.csv`. |

Notes and simplifications:
- This step loads the clean layer only. The dirty files in `data/raw/dirty` are loaded as text into a separate `raw` schema in the data-engineering step.
- Empty CSV fields load as NULL, which matches the nullable columns. `True` and `False` load as booleans.
- The loader truncates only the 11 `core` tables.

## The raw layer (schema `raw`)

`python scripts/load_raw.py` loads the 11 files of `data/raw/dirty` into the `raw` schema of PostgreSQL. It is the first of three layers: `raw` (as delivered), `staging` (typed and deduplicated) and `core` (constraint-checked).

| Aspect | Design |
|---|---|
| Types | Every data column is `text`, so defective values such as `01/02/2024` in a date column, a discount of `1.5` or a negative quantity load without being rejected. |
| Columns | Same names and order as the `core` tables, so the cleaning step maps them one to one. |
| `_row_id` | An identity column that keeps each row's position in the source file. It is the lineage key back to the file. |
| `raw.load_log` | One row per table: source file name, SHA-256 of the file, rows loaded and load time. |
| Empty fields | An unquoted empty CSV field loads as NULL. |
| Reloading | Each load drops and recreates the raw tables in one transaction. A failed load leaves the previous layer unchanged. |
| Not loaded | `defect_manifest.csv`. The cleaning pipeline must never read it. It exists only to score the pipeline. |

Notes and simplifications:
- No cleaning happens in this layer. Duplicates, missing values and invalid values are all present, exactly as delivered.
- The raw tables have no constraints beyond the primary key on `_row_id`.
- `reconcile_raw` checks row counts against the files, column names against `core`, and the stored hash against the file.

## The staging layer (schema `staging`)

`python scripts/build_staging.py` turns the raw layer into typed, deduplicated staging tables for `customers`, `orders`, `order_items` and `payments`. It reads only `raw` (and `raw.products` as the product catalogue). It never reads `defect_manifest.csv` or the `core` schema. Each staging row keeps `source_row_id`, the `_row_id` of the raw row it came from.

Every decision is logged in `staging.row_issues` (`table_name`, `source_row_id`, `row_key`, `rule`, `action`). Actions are `fixed`, `flagged` (kept as is and reported), `dropped` (a duplicate key, keeping the lowest `_row_id`) and `quarantined` (kept out of staging). The view `staging.cleaning_summary` counts rows per rule and `staging.quarantine` lists the quarantined rows. A check verifies that every raw row is staged, dropped or quarantined.

| Table | Rule | Action |
|---|---|---|
| all four | `duplicate_key` | Dropped. |
| customers | `country_standardised` | `USA`, `UK`, `UAE` and lower-case spellings mapped to the canonical list. |
| customers | `missing_email` | Flagged and left NULL. The email is not reconstructed from the customer id. |
| customers | `signup_date_imputed_from_neighbours` | A signup date after 2025-12-31 is replaced by the date of the nearest earlier customer with a valid date, because ids follow signup order. It is an estimate. |
| orders | `date_format_standardised` | The slash format is inferred from the whole column (one part never exceeds 12, the other does). Each parsed date must lie between the dates of its neighbouring order ids, or the order is quarantined as `unresolved_order_date`. |
| orders | `status_case_standardised` | Mapped to `Completed` or `Cancelled`. |
| orders | `discount_recovered_from_items` | A discount above 0.20 is replaced by the valid discount stored on the order's own lines. |
| orders | `missing_customer_id`, `unknown_customer_id`, `customer_quarantined` | Quarantined. Payments and shipments carry no customer id, so the link cannot be recovered. |
| order_items | `quantity_sign_corrected` | Only if the sign flip reproduces the stored line total. |
| order_items | `unit_price_from_catalogue` | A price of 0 is replaced by the product list price. |
| order_items | `line_total_recomputed` | `round(quantity * unit_price * (1 - discount), 2)`. |
| order_items, payments | `order_not_in_staging` | Quarantined with the parent order. |
| payments | `payment_method_case_standardised` | Mapped to the six canonical methods. |
| payments | `amount_recomputed_from_items` | The sum of the order's lines, only if all of its lines are staged. |

Notes and simplifications:
- Quarantined orders carry revenue. The summary script reports it as revenue held back, so it is never silently lost.
- The date check relies on order ids being assigned in order-date order, which is true of this dataset.
- Staging has primary keys but not the full `core` constraints. Promotion into `core` is the next step.

## The analytics layer (schema `analytics`)

`python scripts/build_analytics.py` builds the third and final layer: `raw` (as delivered), `staging` (typed and cleaned) and `analytics` (constraint-checked). It has the same 11 tables and constraints as `core`, because its DDL is `sql/schema.sql` rewritten for the `analytics` schema. All later analysis, models and the dashboard read `analytics`.

| Table | Source |
|---|---|
| customers, orders, order_items, payments | The cleaned `staging` tables. |
| suppliers, products, purchase_orders, inventory_daily | The unchanged `raw` tables, cast from text to the proper types. |
| refunds | `raw.refunds`, minus refunds whose payment was quarantined. |
| shipments | `raw.shipments`, minus shipments whose order was quarantined. |
| daily_metrics | Recomputed by SQL from the `analytics` tables. It has the same 20 columns as before. |
| promotion_log | One row per knock-on quarantined refund or shipment (`table_name`, `row_key`, `rule`, `action`). |

`core` is not touched. It remains the ground truth used only to evaluate the pipeline. The promotion never reads `core` or `defect_manifest.csv`.

Notes and simplifications:
- Revenue in `analytics` is lower than ground truth by exactly the revenue of the quarantined orders (about 0.9%). Any figure from this layer is "cleaned-layer revenue".
- Six imputed signup dates differ from ground truth by about one day.
- `purchase_orders` and `inventory_daily` are unchanged, so they still reflect the demand of the quarantined orders. They are not re-derived from the cleaned orders.
- A constraint violation during the build rolls the whole build back.
